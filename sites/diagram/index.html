Course Generation Documentation

Technical documentation for the AI-powered course generation system

System Overview

Mirai's course generation system uses a hierarchical, multi-phase approach to transform user inputs into complete, structured course content. The system is built on a strict contract architecture where Protocol Buffers define all data structures.

Core Architecture Principles

  • Single Source of Truth (SSOT): Proto files define all contracts
  • Schema-First Development: Define interfaces before implementing logic
  • Compile-Time Safety: Build failures over runtime errors
  • Multi-Tenant Security: Every query is tenant-scoped via RLS

Input Parameters

Course Configuration

  • Course Title: Name of the course
  • Desired Outcome: What learners achieve after completion
  • Additional Context: Extra instructions for generation

SME Knowledge

  • SME Name: Expert source name
  • Domain: Area of expertise
  • Summary: Knowledge overview
  • Chunks: Discrete knowledge pieces (limited to 5 per call)
  • Keywords: Domain topics and tags

Target Audience

  • Role: Job title or function
  • Experience Level: Beginner, intermediate, advanced
  • Learning Goals: What they want to achieve
  • Challenges: Pain points to address

Phase 1: Outline Generation

Uses a two-call approach to work around Gemini's schema depth limitations.

Why Two Calls? Gemini's structured output has schema nesting limits. By first generating sections (flat), then expanding lessons in parallel, we avoid these limits.

Call 1: Generate Sections

1

Build Prompt

buildSectionsOnlyPrompt() with role, course info, audience, SME knowledge.

2

Call Gemini

Uses flat schema returning sections with lesson titles only.

Calls 2-N: Parallel Section Expansion

3

Parallel Gemini Calls

Each section expanded with: titles, descriptions, durations (5-20 min), 2-4 learning objectives.

4

Merge and Store

Position flags computed (IsFirstInCourse, etc.), stored in MinIO.

Phase 2: Lesson Content Generation

Each lesson generated through three phases with context accumulation.

Job Architecture

  • Parent Job (FULL_COURSE): Tracks overall progress
  • Child Jobs (LESSON_CONTENT): One per lesson, run in parallel

Phase A: Component Planning

buildComponentPlanPrompt() generates 5-8 component types with purposes.

Phase B: Iterative Component Generation

Each component generated with accumulated context from previous components.

Phase C: Segue Generation

  • LESSON_TO_LESSON: 1-2 sentence transition
  • SECTION_TO_SECTION: Preview next section
  • COURSE_CONCLUSION: Congratulations + next steps

Atomic Job Claiming

SELECT FOR UPDATE SKIP LOCKED

Jobs stuck >30 minutes treated as crashed and can be reclaimed.

Parent-Child Tracking

Last child to complete atomically finalizes parent using FOR UPDATE lock.

Real-time Event Streaming

Uses Server-Sent Events (SSE) instead of polling.

Event Types

EventWhen Published
JOB_CREATEDJob added to queue
JOB_UPDATEDProgress changed
JOB_COMPLETEDJob finished
JOB_FAILEDJob encountered error
JOB_KEEPALIVEEvery 15 seconds

Keepalive Requirement: 15-second heartbeat prevents proxy timeouts (Cloudflare ~30s).

Rate Limiting

  • Max RPM: 2000 requests per minute
  • Burst: 100 concurrent requests
  • Max Retries: 3 for rate limit errors

Exponential backoff: 6s, 12s, 24s on 429 errors.
